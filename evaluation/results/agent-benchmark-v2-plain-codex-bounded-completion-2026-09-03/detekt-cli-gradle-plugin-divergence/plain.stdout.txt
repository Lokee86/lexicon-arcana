## Diagnosis

Responsibility most likely lies in the Gradle plugin’s invocation/classloader boundary, not in the third-party rule set or detekt core.

Verified current behavior:

- Gradle resolves `detektPlugins` transitively and assigns it to each task’s `pluginClasspath` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:59-65`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-171`).
- The actual Gradle analysis arguments do not contain `--plugins`. Instead, both execution modes combine `pluginClasspath` with `detektClasspath` to create detekt’s own runtime classloader (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-205`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239`).
- The debug “replicate in CLI” output does add `--plugins`, but only to the printed command—not the executed argument list (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:243-255`). Thus that diagnostic currently describes different classloading semantics from the real Gradle execution.
- Gradle’s outer classloader is globally cached using only the integer hash of the set of classpath paths. File contents are not part of the key, and the cached `URLClassLoader` is retained (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`). Replacing or rebuilding a plugin JAR at the same path can therefore leave Gradle using the previous provider classes and embedded configuration.
- Because no real `--plugins` argument was supplied, CLI parsing leaves `args.plugins` empty (`detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85`), and the processing specification forwards that empty collection (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65`). Core consequently falls back to its own classloader rather than creating a dedicated plugin loader (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:32-44`).
- Both rule providers and plugin-supplied `config/config.yml` resources are read through that selected plugin loader (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-13`, `detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-45`). A stale loader therefore explains both “rule set missing” and “configured like an older/different JAR.”
- The baseline and generate-config tasks repeat the same combined-classpath transport, so the defect is not limited to the main analysis task (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:187-206`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektGenerateConfigTask.kt:49-71`).

In contrast, a real CLI `--plugins` invocation places the paths into the processing specification. Core then creates a child `URLClassLoader` for those JARs and closes it after processing (`detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65`, `detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:36-54`). That loader lifecycle is the causal CLI/Gradle divergence.

## Smallest correct fix boundary

Proposed design:

1. Add a Gradle-side CLI argument representation for `--plugins`, joining resolved paths with `File.pathSeparator`; that matches the CLI splitter (`detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:68-70`).
2. Include it in the arguments for `Detekt`, `DetektCreateBaselineTask`, and `DetektGenerateConfigTask`.
3. Pass only `detektClasspath` to `DetektWorkAction`/`DefaultCliInvoker`; do not place `pluginClasspath` in the cached outer loader.
4. Remove the special print-only plugin argument from `printCliCommand`, since the real argument list would now already contain it.

The production boundary is therefore the three Gradle task classes plus `CliArgument.kt`. Core, CLI parsing, `RuleSetProvider`, third-party packaging, and the compiler-plugin path should remain unchanged. Merely changing the cache’s integer key would not address same-path JAR replacement or restore CLI-equivalent plugin-loader lifecycle.

## Verification plan

- Add argument tests proving empty plugin collections emit nothing and multiple JARs emit one `--plugins` value separated by the platform path separator.
- Assert all three Gradle task types pass plugin paths as CLI arguments while their execution classpath contains only `detektClasspath`.
- Add a functional fixture containing a service-registered `RuleSetProvider` and embedded `config/config.yml`. Run once, replace the JAR contents at the same filename with a detectably different rule/config, then rerun in the same Gradle daemon. The second run must observe the replacement without `--stop`.
- Exercise that regression with `detekt.use.worker.api` both disabled and enabled, covering both branches in `Detekt.check()` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239`).
- Verify `detektBaseline` sees the replacement provider and `detektGenerateConfig` includes its updated embedded configuration; config export explicitly consumes parsed plugin paths (`detekt-cli/src/main/kotlin/dev/detekt/cli/runners/ConfigExporter.kt:10-18`).
- Retain existing classloader-cache tests for reuse of the now-stable detekt runtime loader (`detekt-gradle-plugin/src/test/kotlin/dev/detekt/gradle/internal/ClassLoaderCacheSpec.kt:14-39`).

Documentation rationale, distinct from runtime proof: the documentation presents CLI `--plugins` and Gradle `detektPlugins` as equivalent integration mechanisms and tells extension authors not to bundle dependencies detekt already provides (`website/docs/introduction/extensions.mdx:252-278`). Its existing advice to stop Gradle daemons when custom-rule findings disappear is consistent with the persistent-loader diagnosis, but is only a workaround (`website/docs/introduction/extensions.mdx:280-291`).
