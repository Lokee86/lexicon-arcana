## Conclusion

Responsibility most likely lies in the Gradle plugin’s invocation/classloader boundary, not in the third-party rule set or detekt core.

The CLI communicates plugin JARs explicitly through `--plugins`; the Gradle plugin instead adds them to a globally cached execution classpath. That cache is keyed only by file paths, so replacing a JAR at the same path can leave a Gradle daemon using its previously loaded providers and embedded configuration. This explains both symptoms: a provider can appear missing, or an older `config/config.yml` can remain effective.

## Verified current behavior

- `detektPlugins` is a resolvable, transitive Gradle configuration, and its files are wired into each analysis, baseline, and configuration-generation task as `pluginClasspath` (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:59-65`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-172`).

- The CLI defines `--plugins` as JAR paths and transfers those paths into the processing model (`detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85`, `detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65`). Core then constructs a plugin-specific `URLClassLoader`; processing settings close loaders created from paths after the run (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:22-55`, `detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:57-61`).

- Gradle’s real analysis arguments contain no equivalent plugin argument. Both execution branches combine `detektClasspath` and `pluginClasspath` into the launcher classpath (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-206`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239`). Curiously, the debug-only reproduction command synthesizes `--plugins`, so the command printed to users does not represent how Gradle actually loads those JARs (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:243-255`).

- Baseline creation and configuration generation repeat the same classpath-based loading behavior (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:152-206`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektGenerateConfigTask.kt:43-71`).

- `DefaultCliInvoker` obtains its isolated loader from the global cache before reflectively invoking the CLI (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-74`). The cache key is only `HashSet(classpath).hashCode()`; neither file contents, size, nor modification time participates, and cached loaders are retained globally (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`).

- Rule providers are discovered through the selected plugin loader (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-39`). The same loader supplies every plugin’s embedded `config/config.yml`, and that configuration is subsequently selected by rule-set ID (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-53`, `detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:24-40`).

Therefore, the causal explanation is an inference directly from the verified lifecycle: after a JAR has been loaded, rebuilding it at the same pathname leaves the Gradle cache key unchanged. Java cannot redefine already loaded provider classes in that cached loader, and resource lookup may likewise continue through the old JAR state. A standalone CLI process follows the explicit-path loader path afresh.

## Smallest correct fix boundary

The fix should remain entirely in `detekt-gradle-plugin`:

1. Add an internal `PluginsArgument(FileCollection)` alongside the existing CLI argument adapters, emitting `--plugins` plus absolute JAR paths separated with `File.pathSeparator`. That matches the CLI’s `PathSplitter` contract (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/CliArgument.kt:40-69`, `detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:68-76`).

2. Include that argument in `Detekt`, `DetektCreateBaselineTask`, and `DetektGenerateConfigTask`.

3. Pass only `detektClasspath` to `DetektWorkAction`/`DefaultCliInvoker`; remove `pluginClasspath` from the launcher classpath in both worker and non-worker branches.

This restores CLI-equivalent ownership: the cached loader contains the stable detekt runtime, while core creates a fresh plugin loader from current paths for each invocation. All three tasks belong in the boundary because otherwise analysis, baseline creation, and generated configuration would continue to disagree. No changes are indicated in `ServiceLoader` discovery, rule configuration, the tooling API, or the third-party JAR format; existing core tests already verify that explicit plugin paths load both custom providers and embedded defaults (`detekt-core/src/test/kotlin/dev/detekt/core/rules/RuleSetsSpec.kt:88-101`, `detekt-core/src/test/kotlin/dev/detekt/core/tooling/DefaultConfigProviderSpec.kt:34-67`).

The documentation presents CLI `--plugins` and Gradle `detektPlugins` as equivalent integration mechanisms (`website/docs/introduction/extensions.mdx:252-278`). It also recommends stopping Gradle daemons when custom-rule violations disappear (`website/docs/introduction/extensions.mdx:280-290`). That workaround corroborates the classloader-lifetime diagnosis, but it is documentation rationale rather than implementation evidence.
