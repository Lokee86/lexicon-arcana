## Conclusion

Assuming the CLI and Gradle runs use the same detekt version and effective YAML settings, responsibility most likely lies in the Gradle plugin’s invocation/classloader boundary—not in third-party `RuleSetProvider` discovery or core rule configuration.

The Gradle task ultimately invokes the same `dev.detekt.cli.Main.buildRunner` used by the CLI, but it supplies plugins differently: CLI plugin JARs become explicit extension paths, whereas Gradle puts them into a globally cached execution classloader and passes no `--plugins` argument (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-74, detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-206, detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239).

## Verified current behavior

- `detektPlugins` is a resolvable, transitive Gradle configuration, and it becomes each task’s `pluginClasspath` (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:59-65, detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-171).
- The CLI’s supported contract is `--plugins`; parsing records those JAR paths in `CliArgs.plugins`, and `createSpec` installs them with `extensions.fromPaths` (detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85, detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65).
- The Gradle analysis task does not create a plugin argument. Its argument list includes input, compiler, configuration, rules, and report options, but not `pluginClasspath` (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-206). Instead, both execution modes combine `detektClasspath` and `pluginClasspath` into the classpath passed to `DefaultCliInvoker` (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239).
- Curiously, Gradle’s debug-only reproduction command displays `pluginClasspath` as `--plugins`, even though actual execution does not use that argument (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:243-255). This is strong evidence that CLI-equivalent plugin-path semantics are intended.
- Core service discovery loads `RuleSetProvider` implementations from `ProcessingSettings.pluginLoader` (detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-13). Explicit extension paths create a dedicated `URLClassLoader`, parented by detekt’s classloader, which is closed after processing; absent explicit paths, core falls back to its own classloader (detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:29-55).
- Plugin-provided `config/config.yml` resources are also read through that plugin loader, so selecting an old or wrong loader can affect both whether the provider exists and which defaults appear to configure it (detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-45).
- Gradle’s execution loader is globally cached. Its key is only the integer hash code of the set of file paths; neither the full set nor file contents are retained in the key (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27). Consequently:
  - distinct classpaths with colliding set hash codes can receive the wrong loader;
  - replacing a locally built plugin JAR at the same path can reuse a loader that has already loaded its old classes/resources.
- Existing cache tests verify path equality, path difference, and order independence, but do not cover hash collisions or replacement of a JAR at an unchanged path (detekt-gradle-plugin/src/test/kotlin/dev/detekt/gradle/internal/ClassLoaderCacheSpec.kt:14-39).

A clean-daemon, first-run failure is not explained merely by ServiceLoader: on the first execution the combined parent classloader should expose the plugin. In that case, first rule out input differences:

- Gradle automatically selects the root project’s `config/detekt/detekt.yml` when present (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:53-57).
- Custom plugin defaults are merged when configuration is empty or `buildUponDefaultConfig` is enabled; a non-empty explicit configuration with that option disabled does not receive those defaults (detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:43-75).
- Rule activation is derived from the selected ruleset/rule subconfiguration, with individual rules inactive by default unless configuration activates them (detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:30-74).

Thus, a CLI invocation without `--config` and a Gradle invocation that auto-selects a project YAML are not equivalent.

## Proposed fix boundary

The smallest robust boundary is the classic Gradle plugin’s argument/classloader assembly:

1. Add an internal `PluginsArgument` alongside `ConfigArgument`, serializing `pluginClasspath` with `File.pathSeparator`, matching the CLI splitter (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/CliArgument.kt:138-145, detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:68-70).
2. Include it in analysis, baseline, and generate-config argument lists.
3. Pass only `detektClasspath` to `DefaultCliInvoker`; let core create and close the plugin loader through the existing `--plugins` path.
4. Apply the same separation in worker and non-worker branches. Baseline and config generation currently combine the two classpaths in the same way as analysis (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:187-206, detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektGenerateConfigTask.kt:49-71).

This confines the behavioral fix to `detekt-gradle-plugin`; core discovery, configuration merging, and the third-party API need no change. It also removes mutable third-party JARs from the global execution-loader cache.

If the implementation retains the combined-classpath design, the narrower fallback is to repair `DefaultClassLoaderCache`: use a collision-safe immutable classpath key and account for in-place content changes. Changing only `Int` to `Set<File>` fixes collisions but does not fix a rebuilt JAR at the same path, so it is insufficient for the full reported symptom.

## Verification plan

- Add argument unit tests for zero, one, and multiple plugin JARs, including Windows path-separator behavior.
- Add a TestKit fixture containing a minimal service-registered `RuleSetProvider` and `config/config.yml`. Run CLI and Gradle with the same source, YAML, flags, and detekt version; assert identical registered rulesets and findings. Debug logging already prints registered provider class names (detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:34-38).
- In one long-lived Gradle daemon, run with plugin JAR version A, replace that same path with version B containing a distinguishable provider/rule/default configuration, and rerun. The second execution must observe B without `gradle --stop`.
- Exercise two projects/tasks with different plugin classpaths, including deliberately colliding Java file-set hash codes if the cache remains, and assert that neither task sees the other plugin.
- Parameterize functional coverage with `detekt.use.worker.api=false` and `true`, because the task has separate submission paths (detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239).
- Cover `detekt`, baseline creation, and config generation; config generation explicitly uses plugin paths to collect contributed defaults on the CLI path (detekt-cli/src/main/kotlin/dev/detekt/cli/runners/ConfigExporter.kt:8-18).
- Add configuration-control cases: explicit activation must run the rule; a non-empty YAML omitting it with `buildUponDefaultConfig=false` should remain inactive; enabling `buildUponDefaultConfig` should merge the plugin default. This prevents an expected configuration difference from being mistaken for a loading regression.

Documentation rationale, not proof of the defect: the extension guide requires a plugin JAR to omit dependencies supplied by detekt, says custom rules must be activated, and currently recommends stopping Gradle daemons when custom violations disappear (website/docs/introduction/extensions.mdx:252-290). After the loader fix is verified, that daemon-stop workaround should be removed or narrowed.
