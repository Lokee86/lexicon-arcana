## Conclusion

Responsibility most likely lies in the Gradle plugin’s classloader lifecycle, specifically `DefaultClassLoaderCache`, rather than in the third-party `RuleSetProvider`, configuration parser, or analysis engine.

The Gradle plugin puts third-party artifacts on detekt’s long-lived invocation classpath. That classloader is cached globally using only an `Int` hash of file paths. Rebuilding a rule-set JAR at the same path therefore reuses the old loader, retaining previously loaded provider classes and potentially old bundled `config/config.yml` resources. A command-line invocation using `--plugins` instead creates a dedicated plugin loader, explaining why the CLI sees the current JAR.

## Verified current behavior

1. `detektPlugins` is a resolvable, transitive Gradle configuration, and all three task types receive it as `pluginClasspath`: analysis, baseline creation, and configuration generation (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektBasePlugin.kt:59-65`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/plugin/DetektPlugin.kt:137-172`).

2. The analysis task does **not** include `--plugins` in its actual `arguments`. Instead, both execution branches combine `detektClasspath` and `pluginClasspath` into the classpath used to load detekt itself (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:172-205`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:218-239`).

3. The displayed “replicate this task” command separately synthesizes `--plugins`, even though the executed argument list lacks it. Consequently, that diagnostic command does not faithfully describe the classloader arrangement used by Gradle (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:243-255`).

4. Baseline creation and configuration generation use the same combined-classpath arrangement, so this is not confined to the ordinary analysis task (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektCreateBaselineTask.kt:187-206`, `detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/DetektGenerateConfigTask.kt:43-70`).

5. `DefaultCliInvoker` obtains its loader from the process-global `GlobalClassLoaderCache`, reflectively loads `dev.detekt.cli.Main`, and executes the runner through that loader (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/invoke/DetektInvoker.kt:61-74`).

6. The cache identity is only `HashSet(classpath).hashCode()`. It does not include file contents, size, timestamp, or the actual path set as a collision-safe key, and cached loaders are never evicted or closed (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/internal/ClassLoaderCache.kt:12-27`). Therefore:

   - Replacing a JAR at the same path produces the same key.
   - Already loaded provider classes remain the old definitions.
   - A newly added service descriptor/provider can remain invisible.
   - Distinct classpath sets with the same `Int` hash can incorrectly share a loader, although that is a less likely secondary failure.

7. The CLI’s intended route is different. `--plugins` populates `args.plugins`, which is copied into the processing specification (`detekt-cli/src/main/kotlin/dev/detekt/cli/CliArgs.kt:78-85`, `detekt-cli/src/main/kotlin/dev/detekt/cli/Spec.kt:62-65`). Explicit plugin paths cause `ExtensionFacade` to create a dedicated child `URLClassLoader`; processing closes that loader afterward (`detekt-core/src/main/kotlin/dev/detekt/core/settings/ClassloaderAware.kt:22-54`, `detekt-core/src/main/kotlin/dev/detekt/core/ProcessingSettings.kt:57-60`).

8. Provider discovery itself is straightforward: `ServiceLoader` scans `pluginLoader`, filters disabled rule sets, and reports the registered providers in debug output (`detekt-core/src/main/kotlin/dev/detekt/core/rules/RuleSets.kt:11-39`). Rule configuration is then selected from the provider’s rule-set subtree and each rule’s subtree (`detekt-core/src/main/kotlin/dev/detekt/core/RuleDescriptor.kt:24-74`).

9. Configuration can also appear stale because default configuration assembly reads every `config/config.yml` resource visible through the plugin loader (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/DefaultConfigProvider.kt:32-45`). Those defaults participate when no explicit configuration exists or `buildUponDefaultConfig` is enabled (`detekt-core/src/main/kotlin/dev/detekt/core/tooling/ProcessingSpecSettingsBridge.kt:43-75`).

10. Existing cache tests cover identical paths, different paths, order-insensitivity, and concurrent lookup, but not replacement of a JAR’s contents at an unchanged path (`detekt-gradle-plugin/src/test/kotlin/dev/detekt/gradle/internal/ClassLoaderCacheSpec.kt:14-73`).

## Documentation rationale, not implementation proof

The extension guide documents `ServiceLoader` registration and recommends a compile-only dependency on `detekt-api` (`website/docs/introduction/extensions.mdx:11-36`). It presents CLI extensions through `--plugins` and Gradle extensions through `detektPlugins` (`website/docs/introduction/extensions.mdx:252-278`). Most significantly, it already advises stopping Gradle daemons when custom-rule violations disappear (`website/docs/introduction/extensions.mdx:280-291`). That workaround is consistent with clearing the global loader cache, but source behavior above is the actual proof.

## Proposed fix boundary

The smallest correct ownership boundary is `detekt-gradle-plugin`; neither `detekt-core`, the CLI parser, nor the extension API needs behavioral changes.

The preferred fix is at the argument/classpath seam:

- Add a `PluginsArgument` alongside the other `CliArgument` implementations. It should emit `["--plugins", paths joined with File.pathSeparator]`, matching the CLI’s `PathSplitter` contract (`detekt-cli/src/main/kotlin/dev/detekt/cli/ArgumentConverters.kt:68-70`).
- Include that argument in `Detekt`, `DetektCreateBaselineTask`, and `DetektGenerateConfigTask`.
- Pass only `detektClasspath` to `DetektWorkAction`/`DefaultCliInvoker`; do not add `pluginClasspath` to detekt’s cached parent loader.
- Retain `pluginClasspath` as an `@Classpath` task input so Gradle still invalidates tasks when artifacts change (`detekt-gradle-plugin/src/main/kotlin/dev/detekt/gradle/Detekt.kt:71-75`).
- Generate the debug replication command from the actual arguments rather than separately reconstructing `--plugins`.

This preserves caching for the stable detekt runtime while delegating extension loading to the existing run-local plugin loader, making Gradle use the same extension contract as the CLI.

A narrower tactical alternative is to make `DefaultClassLoaderCache` content-aware and collision-safe, replacing and closing loaders when contents change. That can fix same-path staleness, but hashing the entire detekt-plus-plugin classpath is potentially expensive, metadata-only keys are not fully correct, and plugins would remain attached to the daemon-level detekt loader. Explicit plugin-path transport is the cleaner parity fix.
